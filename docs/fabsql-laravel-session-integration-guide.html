Laravel Session 整合手冊

將尚未加入 FabSQL 的既有 Laravel ERP，改造成沿用既有登入 Session 的唯讀 Schema 與 Query API。

Laravel 8.83.29 PHP 7.4.33 ERP Session No JWT SELECT Only

1. 目標與完成後架構

此方案直接沿用 ERP 已存在的登入與 Session，不建立新的 FabSQL 登入方法。

保留既有登入 不修改 ERP User model、登入頁與 Session 寫入流程。
不使用 JWT 不需要 api_users、login、refresh 或 Bearer token。
路由放在 web.php 使用 Laravel web middleware group 取得 Session。
唯讀查詢 後端只接受結構化 Query Model，編譯為參數化 SELECT。

完成後的路由

Method 路徑 用途 驗證
GET /fabsql/ FabSQL 前端 依網站需求
GET /fabsql/health 服務與資料庫健康檢查 公開
GET /fabsql/schema/databases 資料庫清單 ERP Session
GET /fabsql/schema/tables 資料表清單 ERP Session
GET /fabsql/schema/tables/{tableName}/columns 欄位清單 ERP Session
POST /fabsql/query/run 執行唯讀 Query Model ERP Session
前端 Session URL 若網站為 http://jl.test，環境設定應填 http://jl.test/fabsql，不要加上 /health 或 /api。

2. 整合前提

  • ERP 登入流程已可正常使用。
  • 已有可判斷登入狀態的 auth middleware。
  • routes/web.php 由 web middleware group 載入。
  • web group 已啟動 Cookie 與 Session。
  • 已有可用的 MariaDB／MySQL database connection。
  • 資料庫帳號可以讀取目標資料庫與 INFORMATION_SCHEMA。

典型的 web middleware group：

'web' => [
  \App\Http\Middleware\EncryptCookies::class,
  \Illuminate\Cookie\Middleware\AddQueuedCookiesToResponse::class,
  \Illuminate\Session\Middleware\StartSession::class,
  \Illuminate\View\Middleware\ShareErrorsFromSession::class,
  \App\Http\Middleware\VerifyCsrfToken::class,
  \Illuminate\Routing\Middleware\SubstituteBindings::class,
],
未登入回應必須可辨識 FabSQL 前端以 HTTP 401 判斷 Session 已失效。若 ERP 自訂 middleware 在未登入時仍回傳 HTTP 200， 應只針對 /fabsql/* JSON request 改回 401，不要破壞其他 ERP 畫面契約。

3. 整合前先備份

至少備份：

routes/web.php
config/database.php
config/cors.php
config/session.php
app/Http/Kernel.php
app/Http/Middleware/VerifyCsrfToken.php

若專案使用 Git，先確認工作區：

git status -sb

不要覆蓋目標專案原本的 User model、登入流程、Session 邏輯或 auth middleware。

從已完成的 /Users/jimmywon/Herd/api.jl 複製以下 8 個檔案到目標 Laravel 專案的相同位置：

檔案 用途

也不需要：

  • /api/login、/api/refresh、/api/logout。
  • 修改 App\Models\User。
  • 建立 api_users 或安裝 JWT 套件。

5. 設定資料庫 Connection

確認 config/database.php 已存在 FabSQL 要使用的 connection。參考專案的名稱是 jl。 

<?php

return [
  'connection' => 'jl',
  'maximum_result_rows' => 200,
  'maximum_filter_depth' => 20,
];

若目標專案使用不同名稱，只修改 config/fabsql.php 的 connection。 資料庫密碼仍由 config/database.php 與 .env 管理。

最小資料庫權限 建議 FabSQL connection 只授權 SELECT 與必要的 INFORMATION_SCHEMA 讀取，不要授權 INSERT、UPDATE、DELETE、 DROP 或 ALTER。

6. 在 web.php 加入 Session 路由

在 routes/web.php 頂部加入：

use App\Http\Controllers\Api\FabSql\QueryController;
use App\Http\Controllers\Api\FabSql\SchemaController;

加入以下路由：

Route::get('/fabsql/health', [
  SchemaController::class,
  'health',
]);

Route::group([
  'prefix' => 'fabsql',
  'middleware' => 'auth',
], function () {
  Route::get('/schema/databases', [
    SchemaController::class,
    'databases',
  ]);

  Route::get('/schema/tables', [
    SchemaController::class,
    'tables',
  ]);

  Route::get('/schema/tables/{tableName}/columns', [
    SchemaController::class,
    'columns',
  ]);

  Route::post('/query/run', [
    QueryController::class,
    'run',
  ]);
});
路由位置 health 放在 auth group 外；其他四個 API 都必須在 auth group 內。路由放在 web.php，因為 Laravel 的 api.php 預設是無狀態 middleware group。

若 JWT API 仍存在，兩組可以同時保留：

/api/schema/...      JWT
/fabsql/schema/...   ERP Session

URI 不同，不會互相覆蓋。

7. 沿用既有 auth Middleware

'middleware' => 'auth' 直接呼叫目標 ERP 已有的 驗證邏輯。FabSQL 不限定 Session key，只要求 middleware 能判斷目前 request 是否已登入。

參考 api.jl 會讀取 ERP Session 的 _userid；只要 ERP 登入已寫入該 Session， FabSQL 受保護路由即可通過。

若使用 Laravel 標準 guard，確認：

'guards' => [
  'web' => [
    'driver' => 'session',
    'provider' => 'users',
  ],
],

驗證成功標準：

  1. 未登入不能存取四個受保護 API。
  2. 登入 ERP 後，同一瀏覽器可以存取。
  3. Session 過期後回傳 HTTP 401 JSON。

8. 檢查 CSRF

POST /fabsql/query/run 位於 web.php。標準 Laravel 會對 POST 執行 CSRF 驗證，但目前 FabSQL fetch 尚未送出 CSRF header。

目標 ERP 已停用 CSRF

不需額外修改。現在的 api.jl 屬於此情況。

目標 ERP 保留標準 CSRF

不要為 FabSQL 全域關閉 CSRF。若要讓目前前端直接使用，可在 app/Http/Middleware/VerifyCsrfToken.php 只排除唯讀查詢端點： 

protected $except = [
  'fabsql/query/run',
];
不要排除 fabsql/* 例外只放 fabsql/query/run。更嚴格的方案是保留 CSRF，並修改前端送出 X-XSRF-TOKEN，之後再重新 編譯。

9. Session Cookie 與 CORS

建議：前端與 API 使用同一 Origin

ERP 登入：http://jl.test/login
FabSQL 前端：http://jl.test/fabsql/
FabSQL API：http://jl.test/fabsql/health

這是最簡單且穩定的方式，通常不需要額外 CORS，也不需要跨 子網域分享 Cookie。

跨子網域

若前端是 jl.test，API 是 api.jl.test，Session Cookie 必須可供兩個 子網域使用： 

SESSION_DOMAIN=.jl.test
SESSION_SECURE_COOKIE=false

正式 HTTPS：

SESSION_DOMAIN=.example.com
SESSION_SECURE_COOKIE=true

同一主網域且同一 URL scheme 通常可維持 same_site = lax。真正跨站時通常需要 SameSite=None，並且必須使用 HTTPS Secure Cookie。

Credentialed CORS

return [
  'paths' => [
    'fabsql/*',
  ],
  'allowed_methods' => [
    'GET',
    'POST',
    'OPTIONS',
  ],
  'allowed_origins' => [
    'http://jl.test',
  ],
  'allowed_origins_patterns' => [],
  'allowed_headers' => [
    'Accept',
    'Content-Type',
    'X-CSRF-TOKEN',
    'X-XSRF-TOKEN',
  ],
  'exposed_headers' => [],
  'max_age' => 0,
  'supports_credentials' => true,
];
不要使用萬用 Origin Credentialed request 不應將 allowed_origins 設為 *，請列出實際前端 Origin。

11. FabSQL 前端環境設定

  1. 先使用相同瀏覽器登入 ERP。
  2. 開啟 http://jl.test/fabsql/。
  3. 開啟「環境設定」。
  4. 在「連線與驗證」選擇 Session。
  5. Laravel 網址輸入 http://jl.test/fabsql。
  6. 按下「套用」。

Session 模式不需要 Email 或密碼。所有 Session request 都會使用： 

credentials: 'include'

12. 清除 Cache 與驗證

清除 Laravel Cache

php artisan optimize:clear

若 Laravel 版本不支援，分別執行：

php artisan route:clear
php artisan config:clear
php artisan cache:clear

檢查路由

php artisan route:list --path=fabsql

預期：

GET|HEAD  fabsql/health
GET|HEAD  fabsql/schema/databases
GET|HEAD  fabsql/schema/tables
GET|HEAD  fabsql/schema/tables/{tableName}/columns
POST      fabsql/query/run

公開 Health

curl -i http://jl.test/fabsql/health

未登入也應回傳 HTTP 200 與：

{
  "status": "ok",
  "database": {
    "name": "資料庫名稱",
    "version": "MariaDB 版本"
  }
}

Session 驗證

  1. 無痕視窗請求 schema，預期 HTTP 401。
  2. 登入 ERP 後，在同一瀏覽器重新請求，預期 HTTP 200。
  3. Network 應顯示 request 帶有 ERP Session Cookie。
  4. 加入資料表與欄位後按 Run，確認 POST query 回傳 200。
  5. 從 ERP 登出後再請求，前端應顯示「需要先登入 ERP」。

建議測試案例

  • health 未登入仍是 200。
  • 四個保護 API 未登入都是 401。
  • 已登入可取得 databases、tables、columns。
  • 已登入可執行結構化 Query Model。
  • Query compiler 只能產生 SELECT。
  • 不存在的 database 或 table 回傳明確錯誤。
  • 結果筆數受 maximum_result_rows 限制。
測試檔注意事項 目前 api.jl 的 Feature tests 已在後續階段改為 JWT /api/* 測試，不應原封不動複製成 Session 測試。Session Feature test 必須依目標 ERP 的登入 Session key 調整。

13. 常見問題

現象 可能原因 處理方式
JS／CSS 404 Vite base 仍是 / 使用 base: '/fabsql/' 重新編譯
送到 /fabsql/api/health 舊版前端或未選 Session 更新前端並選 Session
health 404 路由未載入或 route cache 清除 cache 並檢查 route:list
health 正常但 schema 401 Session Cookie 未送出 先登入 ERP，檢查 Cookie domain
schema 回傳 302 或 HTML auth 導向登入頁 JSON request 改回 HTTP 401
未登入卻回 HTTP 200 ERP 自訂錯誤格式 只對 /fabsql/* 回 401
query 419 CSRF token 缺失 窄範圍排除 query/run 或讓前端送 token
CORS 錯誤 前端與 API 不同 Origin 設定明確 Origin 與 credentials
已登入但 API 看不到 Session host-only Cookie 或 SameSite／Secure 不符 優先改同 Origin，或調整 Session Cookie
MariaDB 無法連線 FabSQL connection 名稱錯誤 改成 config/database.php 的實際名稱

14. API 異動紀錄

每個整合 FabSQL 的 Laravel 專案都應建立 FABSQL_CHANGES.md，至少記錄：

狀態 檔案 用途
新增 config/fabsql.php Connection 與限制
新增 app/Services/FabSql/*.php Schema、validation、compiler、executor
新增 app/Http/Requests/FabSql/RunQueryRequest.php Request validation
新增 app/Http/Controllers/Api/FabSql/*.php Schema 與 Query API
修改 routes/web.php Session 路由
視情況修改 database、CORS、Session、CSRF、Authenticate 依目標 ERP 環境調整

記錄 SHA-256：

shasum -a 256 routes/web.php
shasum -a 256 config/fabsql.php
shasum -a 256 app/Services/FabSql/*.php
shasum -a 256 app/Http/Requests/FabSql/RunQueryRequest.php
shasum -a 256 app/Http/Controllers/Api/FabSql/*.php

Session、Cache、Log 與 PHPUnit cache 應標示為 runtime 檔案，不要誤列成人工 source code 修改。

15. 回復方式

  1. 從 web.php 移除兩個 controller import。
  2. 移除 health 與 prefix => fabsql route group。
  3. 移除本手冊第 4 節的 8 個 FabSQL 後端檔案。
  4. 回復因 FabSQL 修改的 CORS、Session 或 CSRF 設定。
  5. 移除 public/fabsql 靜態前端。
  6. 執行 php artisan optimize:clear。
  7. 在 FABSQL_CHANGES.md 記錄回復日期與檔案。
不要移除 ERP 基礎功能 不要刪除 ERP 原本的登入、Session、auth middleware 或資料庫 connection。
